# Ekiben Project Tracker — brief

## Context
Ekiben is a Baltimore restaurant. This tracker is part of a 5-week AI Builder fellowship (mid-October to just before Thanksgiving 2026). It tracks fellowship projects and company projects used by Ekiben employees. It should be understandable to staff and maintainable after the fellowship. Other candidate Ekiben tools are out of scope.

## Requirements (current)
- **Accounts:** sign in with a verified email at an allowed Ekiben domain (configurable; `ekibenbaltimore.com` is provisional). Roles are member and admin. Everyone defaults to member; admins come only from a private allowlist managed out of band.
- **Visibility:** a member sees projects they created and projects an admin assigned to them. An admin sees all. Enforced in the database.
- **Projects:** name, description, creator, multiple assignees, status (not started, in progress, stuck, done, cancelled; the stored value is still `blocked`), a short current phase (24 characters) and a 0-100 progress value that drives the progress ring, priority, optional deadline, next step, timestamps, threaded comments, and dated history. Archive or cancel, never delete.
- **Editing (defaults to confirm):** creators edit their own projects; assignees update status, phase, progress and next step and comment; authors can edit and delete their own comments (and nobody else can); anyone who can see a project can reply; only admins assign and reassign; anyone who can see a project can comment.
- **History:** append-only, written in the same transaction as each change.
- **Weekly summary:** in-app, compares each project at Monday 00:00 `America/New_York` with now; members see only their projects; deterministic, no AI.
- **Privacy:** synthetic demo data only; visible reminder not to enter customer or financial details; no secrets in git.
- **Deployment:** an online demo on Vercel with a hosted PostgreSQL and SMTP, auto-deploying from GitHub `main`. A Vercel project and production deployment exist (https://ekiben-project-tracker.vercel.app) with the GitHub repo connected. The database will be hosted on Supabase; sign-in cannot work until it and an SMTP sender are configured. Details and next steps in [PRIVATE-DEMO.md](PRIVATE-DEMO.md). Production is a separate decision.

Permissions in detail: [ACCESS.md](ACCESS.md). Admin procedures: [ADMIN.md](ADMIN.md).

## Decisions
- **Next.js + PostgreSQL with SQL migrations.** Runs locally with what is installed; portable to a managed Postgres. Supabase was not used because its local stack needs Docker, which is not installed.
- **Rules in the database** (RLS + triggers), mirrored in server code and UI.
- **Custom sign-up and password sign-in** (no identity vendor chosen). Sign-up and password reset prove the email with a one-time code and set a password in the same step (migration 006); later sign-ins are email + password. Passwords are hashed with scrypt in the app; the database stores salt and hash in a table the app role cannot read. Defaults (not Ekiben requirements): 10-128 characters, 5 wrong attempts lock an account for 15 minutes (which also lets someone lock out a known address; acceptable for a demo), no common-password list, no multi-factor. Trade-off: custom auth needs outside review before real use.
- **Summary rebuilt from the event log**, so start-of-week state needs no snapshot job.
- **Hosting: Vercel + Supabase (as plain Postgres) + a separate SMTP sender; the app's own sign-in is kept.** Supabase's custom SMTP setting only serves Supabase Auth, which this app does not use. Migrations are a deliberate manual step, not run on deploy; owner credentials never go to Vercel; `db:setup` was made portable to non-superuser owners.
- **No AI narrative** in this version.
- **Local-dev exact-email exception.** `DEV_ALLOWED_EMAIL` (set only in the ignored `.env.local`) lets one exact address sign in locally for testing. It is not a domain or list, plus aliases are still rejected, the account is a member, the code and throttle rules still apply, and the app refuses to sign anyone in when it is set in production. It is enforced in the same app check and database function as the domain rule (migration 004).
- **Named exceptions outside the domain.** `ALLOWED_EMAILS` (set in Vercel or `.env.local`, never in the repository) lists full addresses that may sign in besides the allowed domain; it works in production, unlike `DEV_ALLOWED_EMAIL`. Same rules as the domain check: no aliases, verified code, member by default, enforced again in the database functions. Added at the project owner's request so their own existing account keeps working while sign-up is limited to the Ekiben domain.
- **No store selection.** Removed at the project owner's direction; migration 003 drops the store tables and links but keeps existing history rows (history is append-only).
